# BUG-003: 2014 PYQ Duplication — DELETE Pending Approval

## Summary
2014 questions were double-ingested from two sources: `12_Paper_2014.pdf` (official, 129
rows) and `community:Aquib-Nawaz` (secondary/community-transcribed, originally 73 rows).
`question_hash` (exact-text hash) found **zero** matches between the two sources — the two
extractions have different punctuation/OCR normalization, so exact-hash dedup doesn't work
here; fuzzy text similarity was needed instead.

## Resolved 2026-09-16 — 17 of ~30 candidate rows deleted, rest deliberately left alone

Rahul approved execution. Backed up first (`~/.claude/backups`, backup id #5) before any
deletion. Method: fuzzy-matched (`difflib.SequenceMatcher`, normalized text) every official×
community pair within year=2014. Found 18 pairs at ≥0.85 similarity; before deleting any,
verified `correct_answer` and full options match/near-match for each pair (not just question
text) — this caught 2 pairs that text-similarity alone would have wrongly treated as safe
twins:
- **community#2329 / official#790**: same question, but `official`'s `correct_answer` is
  **NULL** — deleting community here would have destroyed the only known answer. **Not
  deleted, left as-is**, needs a manual repair decision (which text wording to standardize
  on, and confirming the answer).
- The other 17 pairs had matching (or only cosmetically-differing, e.g. case/apostrophe-style)
  options and answers — safe. Deleted the 17 community-sourced duplicates, kept the
  official-PDF version each time. `2014` now has 129 official + 56 community = 185 rows
  (was 205 before this session's OCR-junk cleanup removed 3, then 202 before this dedup).

**Repaired 2026-09-16 (same session, Rahul approved "repair by merging"):** the 8
truncated-official pairs above, plus the missing-answer pair (community#2329/official#790),
were fixed by merging community's fuller content into the official row and then deleting the
now-redundant community row. Backed up first (backup #6 — both the official rows' pre-repair
state and the deleted community rows, so either direction can be reconstructed exactly).

Per-pair repair applied (official id → what was merged in):
- **790**: `correct_answer` was NULL → filled with community's `'d'`. Text/options already fine.
- **920, 793, 785, 786**: `question_text` was missing its numbered list AND `correct_answer`
  was NULL → both merged in from community. Options already matched, left as-is.
- **782**: `question_text` merged in (options/answer already agreed between sources, just
  upgraded `answer_source` to `community_validated` from the weaker `ai_inferred`).
- **897**: official had only 1 of 4 options populated (B/C/D were NULL) and no answer —
  replaced with community's full option set, text, and answer.
- **865**: official's options didn't even fit the question's 3-item list (a "both/neither"
  binary framing against a 3-disease list) — genuinely wrong/mismatched data, not just
  incomplete. Replaced entirely with community's coherent options/text/answer.

Each repaired row's `source_file` was updated to record the dual provenance (e.g. `"12_Paper_
2014.pdf + community:Aquib-Nawaz (text+answer merged in)"`) so this merge is visible directly
on the row, not just in this doc. `answer_source` set to `community_validated` on all 8,
since the real answer/text came from that source in every case.

**community#2318 / official#806 — deliberately NOT merged, still open.** Official's options
imply the underlying list has 4 items ("2 and 4 only", "1, 2, 3 and 4") but community's
question_text only lists 3 ("Terrace cultivation", "Deforestation", "Tropical climate") — one
side is missing a real list item, not just a formatting/OCR difference, and it's not possible
to tell which from these two sources alone. Needs a real independent source (an actual UPSC
2014 GS Paper-I PDF/answer key) to resolve — flagging rather than guessing, per standing
practice for scarce/ambiguous exam data.

**Final 2014 state:** 121 official-only + 8 merged (dual-provenance) + 48 community-only = 177
rows (was 205 at session start, before this session's 3-row OCR-junk removal, 17-row clean
dedup, and this 8-row repair-merge).

Remaining ~15 mid-similarity pairs the fuzzy matcher initially surfaced were manually

code given below") — correctly left untouched, not duplicates.
