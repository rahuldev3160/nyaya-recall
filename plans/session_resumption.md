# Feature Plan: Session Resumption (Resume Later)

**Status:** Deferred — queued for post-exam evaluation
**Priority:** P3
**Logged:** 2026-05-12
**Deferred by:** Rahul — needs cost/scope evaluation after exam

---

## Why this was logged

During planning of the open-ended quiz mode (no fixed question count, "Save & Close" per
question), two options were identified:

- **Option A — Save as complete**: "Save & Close" closes the session as finished with
  questions answered so far. Simple. Built as part of open-ended quiz mode (queue item #5).

- **Option B — Resume later** (this document): "Save & Close" pauses the session. The user
  can return later — on the same device or a different one — and continue from the exact
  question they left off.

Option A was chosen for immediate implementation. Option B is documented here for future
evaluation.

---

## Problem Option B solves

React state is ephemeral — it lives in browser memory only. A page reload, app close, or
device switch wipes which question the user is on, which answers have been selected on
screen, and the full question set for that session.

Currently: generate → answer → close (linear, must complete in one sitting).
Option B: generate → answer → pause → resume → ... → close (interruptible).

Most valuable for:
- Open-ended sessions that span multiple sittings
- Users who study in short bursts across the day
- Cross-device continuity (phone during commute, Mac at desk)

---

## What's needed to build it

### 1. Persist the full question set

Questions are generated by Claude, returned to the frontend, and answered one by one.
Currently, only **answered** questions are written to `session_answers`. Unanswered
questions exist only in React state — they vanish on page reload.

Resumption requires storing the full question set at session creation time.

**Option B1 — localStorage (simpler, device-specific)**
- On session start: save `{ session_id, questions[], currentQ }` to `localStorage`
- On DiagnosticPage load: check localStorage for any open session, offer "Resume"
- Survives: page reload on same browser
- Does NOT survive: browser data clear, incognito, different device

**Option B2 — DB persistence (cross-device, robust)**
- New column: `quiz_sessions.question_cache TEXT` — JSON of full question array
- New column: `quiz_sessions.last_question_index INTEGER`
- On session start: write full question set to DB alongside session creation
- New endpoint: `GET /sessions/{id}/resume` — returns question cache + last index
- Survives: across devices, browser clears, app restarts

### 2. Session lifecycle change

Current lifecycle:
```
POST /quiz/generate  →  answer loop  →  POST /sessions/{id}/close
```

New lifecycle:
```
POST /quiz/generate  →  answer loop  →  POST /sessions/{id}/pause
                                     ↓
                         GET /sessions/{id}/resume  (later)
                                     ↓
                              answer loop continues  →  POST /sessions/{id}/close
```

`quiz_sessions` needs a `status` column: `'active' | 'paused' | 'closed'`

### 3. Frontend: resume detection

On DiagnosticPage load, before showing the subject selector:
1. Check for any `status = 'paused'` session for `user_id = 'user_1'`
2. If found: show banner "Resume: Polity — Q5 of 10, 3 answered"
3. User can resume or discard and start fresh

### 4. Unanswered questions in DB (Option B2 only)

If questions are stored in `quiz_sessions.question_cache`, they can be retrieved on resume.
If using localStorage (Option B1), questions are available only on same device/browser.

## Cost implications

| Concern | Detail |
|---------|--------|
| API cost | Zero — no new Claude calls. Resume just restores state. |
| DB storage | Option B2 adds ~5–10KB per session (question cache JSON). Negligible for SQLite. |
| Build effort | Option B1 (localStorage): ~3–4 hrs. Option B2 (DB): ~8–10 hrs. |
| Scope risk | Changes session lifecycle — every part of the quiz flow needs to handle "paused" state. Skip, expand concept, metacognition capture all touch session state. |

---

## Scope risk detail

The current quiz flow assumes a session is either active or closed. Adding "paused"
introduces a third state that every consumer of session data must handle:

- `score_engine.close_session()` — must reject if session is paused (not closed yet)
- `batch_analyse.py` — must skip paused sessions in aggregation
- `plan_generator.py` — must account for partially-answered sessions when computing coverage
- `difficulty_engine.py` — partial session data should not update difficulty until closed
- Tracker page — must distinguish paused sessions from completed ones in readiness scores

Each of these is a small change, but the blast radius across the codebase is wide.

---

## Decision criteria for picking this up

Build Option B when **all three** are true:

1. Open-ended quiz mode (Option A) is live and Rahul regularly hits the limitation of
   not being able to resume (i.e., he starts open-ended sessions he can't finish)
2. Study sessions regularly exceed 30 minutes (making real interruption likely)
3. Cross-device continuity matters — if phone + Mac are both used for study sessions

If cross-device is not a requirement, Option B1 (localStorage, ~3–4 hrs) is sufficient
and avoids the DB schema and lifecycle changes of Option B2.

---

## Recommended approach when ready

Start with **Option B1 (localStorage)**:
- Lower effort, no DB schema change, no lifecycle refactor
- Covers the primary use case (interrupted session on same device)
- Can be upgraded to Option B2 later if cross-device becomes a requirement

Estimated effort: Option B1 ~3–4 hrs | Option B2 ~8–10 hrs
